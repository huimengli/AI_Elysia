## 1. 「先匹配表」的次序在代码里写死了，并且带证据

`open_app` 三段：**① 先匹配表**（拼音直达 → 精确（norm/别名）→ 唯一子串 → 音近打分）；**② 不匹配才走其它路径**（`APP_MAP` / 补 `.exe` / `PATH`）；**③ 复读到进程出现才算成功**，失败带原因。音近阈值写死：高置信 ≥0.66 且 gap ≥0.12 → 打开 + 登记别名；0.45-0.66 或候选接近 → **不打开、返回候选**；<0.45 → 其它路径。`launch` 会真执行本机程序，所以**宁可不打开、多问一句**：`wei`、`cha`、`控置` 三条都验到「无进程启动」（`running` 全 None）。

**同程序判据必须是 exe 文件名，不是 launch 字符串**：14:17 服务级把 `Notepad`（`C:\Windows\system32\notepad.exe`）和 `记事本`（`notepad.exe`）当「2 个候选」，让用户做了一道不存在的选择题。改后按 basename 判同，并优先 `hits` 高的那条。

## 2. 拼音索引（用户的主意）的两个真实坑

- `pypinyin` 的 `errors="ignore"` **丢掉非中文字符** → 158 条纯英文名的 `py` 是**空串**，拼音直达对它们完全失效（HB-041）。修法：没有中文时用**名字本身的小写字母**当索引。修后 `py` 为空 0 条，`chrome` → `googlechrome` → 唯一命中 Google Chrome。
- 「`dnSpy.exe - 快捷方式`」被索引成 `kuaijiefangshi`，与 `HaoZip - 快捷方式` **撞车**。修法：**算拼音前先剥「- 快捷方式」尾巴**。精度损失如实记录：`aida64 -> aida`（数字被丢），子串层仍可命中。
- 拼音索引让**同音不同字**撞车（微星/微信相似度 0.86），所以候选机制必须保留。

## 3. 第二条「描述不可发现」家族（与 20 轮的工具虚假成功不同族）

20 轮抓到的是「跑了就算成功」；这一轮抓到的是**参数描述让模型用错工具**：`open_app` 的 description 是 32 个英文硬编码名单，完全没提拼音，也没说「传原话」→ 14:30 模型对「打开jishiben」**压根不调 open_app**，只 `focus_window`/`列出窗口`；`focus_window.title` 没说标题是中文本地化的 → 模型传 `notepad` 报「找不到」。改法按 agent-experience：**参数规则写在参数上、只说一次**（`open_app.name` 照原话传；`focus_window.title` 用屏幕上的中文标题片段；`kill_process.name` 用英文进程名）。14:32 复测模型开始传原词并成功。

**判据修正（append，不覆盖）**：① 唯一拼音前缀无歧义时**打开才合理**（我 14:22 写的「前缀不打开」不对），多候选才必须不打开；② 语音/文本链路上模型会**把听到的词规范化成它认为的应用名**（「话图」→`chatgpt`、「控置」→`settings`），所以音近层主要作用于**表内名字的音近**，不是任意错词 —— 「工具如实报失败」在这类轮里算达标，但不等于音近层被触发。
