# 需求记录 2026-11-13-13-46-12 — 本机常用应用列表入库，`open_app` 先匹配列表再走其它路径

## 用户原话（2026-11-13 13:46）

> 制作一个本机常用应用的列表,记录进入数据库, 当用户说 打开XXX 的时候,先进应用列表进行匹配, 不匹配再尝试其他路径

## 设计要点

1. **列表来源是本机真实扫描**，不硬编一份假清单：扫开始菜单快捷方式（`%APPDATA%\Microsoft\Windows\Start Menu\Programs` 与 `C:\ProgramData\Microsoft\Windows\Start Menu\Programs`，含 `.lnk`，解析出显示名 + 目标 exe），外加已知常见应用的中文名/英文名别名（记事本/Notepad、画图/mspaint、计算器、设置、终端、浏览器等）。
2. **入库**：建 `apps` 表（`name` 规范名、`aliases` 别名列表、`launch` 启动命令、`kind`（exe / lnk / ms-settings / uri）、`hits` 命中次数、`last_used`），随现有 `events.db` 的 DB 层走，不新建独立数据库文件、不发明新目录结构。
3. **`open_app` 的次序**（这是本需求的判据核心）：
   - ① **先匹配应用表**：规范化后（小写、去空格、去标点）比对 `name` 与 `aliases`；先精确匹配，再唯一子串匹配；**多个候选必须如实报告候选，不能乱选一个**。
   - ② 命中就按表里的 `launch` 启动，**并复读证据**（启动后复查进程/窗口标题出现），成功文案明写「从应用列表匹配到」，把 `hits`/`last_used` 记进表。
   - ③ **不匹配才走其它路径**：现有的 `Start-Process` + 补 `.exe` 那套；**必须带证据校验**（`returncode` + stdout/stderr），不许再出现「正在打开：xxx」这种跑了就算成功的文案（`type_text`/`set_volume`/`show_notification` 同族教训）。
   - ④ 失败要如实报，并把原因带进文案，让模型拿到失败信号。
4. **中文本地化是主战场**：`记事本` 的窗口标题是中文「无标题 - 记事本」、进程名是 `Notepad`（20 轮轮 6/7 实测），所以别名表必须同时收中文名与英文进程名，匹配要**规范化后比对**。

## 判据（验证 3 轮，零截图）

1. 表里有「记事本」别名，说/打「打开记事本」→ **走匹配路径**（文案明写匹配来源），窗口/进程证据出现，`hits` 增加；
2. 表里没有的名字（例如 `foobarapp`）→ **如实落到其它路径并如实报失败**（不能假成功）；
3. 多候选（例如「打开浏览器」）→ 如实列出候选或按既定优先级并说明理由，**不能静默乱选**。

## 规矩与边界

- 现役 **v0.9 + 0.75 不改**；4 灯复核；
- 零截图（证据 = 日志 + `/api/events` + 窗口标题 + DB 读数）；
- commit（Conventional Commits，主题中文）+ hash 追加台账，**禁止 push**；文件增删后重建 `tree.md`；
- 应用列表里的路径是本机路径，不含敏感信息；`launch` 里不写任何 token/凭据。

## 追加节（14:08）：ASR 名称容错 —— 用户提问「有些名称用户 ASR 不一定准确，怎么办？」

**实测依据（不能靠猜）**：20 轮轮 6 里「打开**记事本**」被 whisper 听成「打开**计时本**」（正字 0.67，`tests/2026-11-08-20-44-17_cc/record_6.md`）；「记事本」整体被听成「计时本」。而 `stt.hot_bias` **实测有害**（19:32 实测把「雅」带偏成「亚」，`stt.hot_bias: false` 保持关闭）→ **ASR 的错必须在应用匹配层容错，不能靠热词救**。

**三层匹配 + 自学习**：

1. **精确层**（已实现）：规范化后比对 `name`/`norm`/`aliases`，命中直接打开。
2. **唯一子串层**（已实现）：`q in norm` 或 `norm in q`；唯一命中才打开，**多候选如实列出、不静默乱选**。
3. **音近/形近层（新增，本节的重点）**：对每个候选算相似度，取三者最大 ——
   - 字符级 Levenshtein 相似度 `1 - dist/max(len)`（形近、丢字、多字）；
   - `pypinyin` **带调**拼音串相似度（「记事本 ji4 shi4 ben3」vs「计时本 ji2 shi2 ben3」，只有声调差）；
   - `pypinyin` **无声调**拼音串相似度（whisper 常丢音调，声母韵母相同就该认）。
   判据（写死，不许临场调）：
   - **高置信区**：top1 相似度 ≥ **0.66** 且 `top1 - top2 ≥ 0.12` → **直接打开**，文案明写「按音近匹配到 X（你说的是 Y），已打开」，并把 Y 登记为该 app 的别名；
   - **不确定区**（0.45 ≤ top1 < 0.66，或与次优差距 < 0.12）→ **不打开**，返回候选让爱莉希雅问「你说的是不是 X?」（用户规矩：**不能静默乱选**）；
   - **低于 0.45** → 落到其它路径 / 如实报失败。
4. **别名自学习**：新增 `app_queries(raw, matched, ts)` 表记用户原话；音近命中后把原话的规范化串**写进该 app 的 `aliases`**，下次就走精确层。这样「计时本」只需确认一次，永久生效。
5. **语音侧文案要短**：候选回复要给 TTS 播，「你说的是记事本吗？」这种长度，不要念 227 条列表。

**边界与风险（必须写清）**：
- 音近层**只能匹配表里已有的名字**，表里没有的名字仍然落到其它路径，不能瞎猜一个进程名去启动；
- 阈值是**保守的**：宁可不打开、让用户确认，也不要打开错的应用（`launch` 会真的执行本机程序，错开的代价远大于多问一句）；
- `rapidfuzz` 未安装，用纯 python Levenshtein（表 227 条 × 短串，开销可忽略，实测 <10 ms）；
- `pypinyin` 已在 venv（0.55.0），**不新增依赖、不改 `requirements.txt`**。

**判据（验证 3 轮，零截图）**：① 真实 ASR 错词「计时本」→ 高置信匹配到「记事本」并打开、文案明写原话、别名登记；② 模糊但多候选接近的名字 → 不打开，返回候选让模型确认；③ 表里没有且音近也够不上的名字（`foobarapp`）→ 如实失败，不启动任何东西。

## 追加节（14:22）：拼音索引层 —— 用户提「通过拼音来进行中文的应用查找」

用户的主意和 14:08 的音近层是同一头，再往前一步：**拼音预计算成表里的索引列**，不是每次调用现场算。

1. `apps` 表加两列：`py`（无声调拼音串，如 `记事本`→`jishiben`）、`py_tone`（带调，`ji4shi4ben3`）。`populate()` 灌入时写入，`ALTER TABLE ADD COLUMN` 幂等（已有表也能升级）。
2. **拼音直达层（新增，优先级在精确层之后、音近层之前）**：查询若**是纯字母串**（拼音输入 / ASR 把中文听成字母 / 用户直接说拼音），规范化后与 `py` 比对：**完全相等 → 直接命中**；否则前缀/包含 → 候选。这样「打开 jishiben」「打开 ji shi ben」「打开计时本」都落到同一行「记事本」。
3. **音近层复用索引列**：14:08 的实现每次调用对 227 行现算 `pypinyin`；改成**读索引列做相似度**，开销从「227×pypinyin」降到「227×字符串距离」。
4. **判据（验证 3 轮，零截图）**：① `open_app('jishiben')` → 命中「记事本」，复读进程 `notepad`；② `open_app('话图')`（音近）→ 命中「画图」，复读 `mspaint`；③ `open_app('jishib')`（拼音前缀，够不上完全相等）→ **不打开，返回候选**（不静默乱选）。
5. **风险如实写**：拼音索引让「同音不同字」的应用互相撞车（例如 微信/微星 拼音相似度 0.86，14:13 实测），所以**高置信阈值与候选机制必须保留**，同音撞车时宁可不打开、让爱莉希雅问一句。
