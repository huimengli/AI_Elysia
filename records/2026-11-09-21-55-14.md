# 2026-11-09-21-55-14 唤醒阈值 0.7 + 唤醒提示音直播 + 工具名汉化

- 提出时间：2026-11-09 21:55:14
- 提出人：用户原话：
  1. 「触发调整成0.7」
  2. 「唤醒后播放固定音频的速度太慢了,按理来讲这部分不会进入tts,直接播放已有音频即可,看看能不能优化一下?」
  3. 「执行工具,在交给tts的时候也应当汉化:我执行了 type_text、press_key => 我执行了 输入文本、按下按钮」

## 现状勘察（开工前实测）

- `config.yaml`：`wake_word.model aili_xiya_v0.3.onnx`、`wake_word.threshold 0.65`（`jarvis/wake.py` 的 `state["threshold"]` 与灯上显示都取该值）。历史：v0.3c 的验收结论是 **阈值 0.7 → recall 0.94 / false-positive 0.09**（`tests/opinion.md` 2026-10-17 小节），改 0.7 与验收结论一致。
- 唤醒提示音路径需要逐处确认：`jarvis/main.py` 唤醒命中后的播报走什么通道（是否调用 `tts`）、有无已缓存音频文件（如 `assets/`、`.tmp` 下的 wav）。若走 TTS 合成，则首字延迟 = 模型 + 合成 + 播放，正是用户抱怨的「太慢」。
- 工具名汉化：`jarvis/tools.py` 的工具名（`type_text`、`press_key`、`get_time` 等）在广播「我执行了 X」时直接用了英文原名，需加「中文显示名」映射，只影响 TTS/网页播报，不改工具本身的 name（schema 与调用不变）。

## 方案

1. **阈值 0.7**：`config.yaml` `wake_word.threshold: 0.7`；`jarvis/wake.py` 的 `state` 在启动时读取，改后需重启 Jarvis 才刷新灯上的 `threshold`（沿用 `run28` 式重启：`Get-NetTCPConnection -LocalPort 7860` 定位 pid 后杀，再隐藏窗口拉起）。
2. **唤醒提示音直播**：把「唤醒成功」提示变成**预生成的固定音频**（一次性用 TTS 生成并落盘为 `assets/wake_answer.wav`，或在仓库里放现成 wav），唤醒命中后**直接播放该文件**，完全绕过 TTS 请求；播放用轻量播放器（本地文件解码 + 已有音频输出路径），不再每次合成。若现在已是固定音频，则优化点在「解码/输出延迟」，改为把音频预加载成内存中的 PCM，唤醒后直接写流。
3. **工具名汉化**：在工具定义处加中文显示名映射（`type_text → 输入文本`、`press_key → 按下按钮`、`get_time → 获取时间`…），广播与 TTS 文案一律用中文名；英文 name 保持不变，`tool`/`tool_result` 事件仍写英文原名，便于检索。

## 验证计划（3 轮，零截图）

① 阈值落盘与生效：读 `config.yaml` + `GET /api/health` 的 `wake.threshold` 为 0.7、`wake.online/listening` 正常；② 唤醒提示音路径不再出现 TTS 请求（事件库/日志中唤醒后无 `tts` 调用，且首字延迟显著下降，用时间戳对比）；③ 工具事件与播报文案：真人/脚本触发一次工具执行，检查广播与网页端显示为「我执行了 输入文本 / 按下按钮」，`events.db` 里 `tool` 行仍为英文原名。结论累积到 `tests/opinion.md`。
